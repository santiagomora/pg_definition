Changelog 06-12-2024
la idea seria seguir el ejemplo de alembic y mezclarlo un poco con las bases de datos de laravel:
    1. tener un stub con los metodos up y down del cual podamos generar un archivo de migracion dado.
    2. el numero de migracion vendria dado por una secuencia interna de la extension en la base de datos. es decir, cada extension tiene un namespace en la base de datos, y dentro de ella, tablas que lleven el seguimiento de las tareas y scripts aplicados en la transferencia.
    3. el script de aplicacion debe detectar cual fue la ultima migracion aplicada y aplicar las migraciones entre esa y el valor actual de la secuencia.

al correr el script para generar una migracion:
    1. se genera una carpeta en la ruta indicada (configurable) que contiene un archivo con un script up y un script down que van a acompanar los cambios que se introduzcan en la migracion. uno para hacerla y otra para deshacerla. la idea es que el estado anterior de la base de datos sea recuperable luego de aplicar la migracion. esto incluye a los datafixes
    2. el script up se aplica antes de aplicar los cambios expuestos por la funcion up del
    3. el script down se aplica antes de aplicar los cambios expuestos por la funcion down del archivo de migraciones


En resumen, del lado de manejo de archivos necesitaremos. De ahora en mas nos referimos a la secuencia como revision:
    1. script para generar la migracion, que actualice la revision en la base de datos para la extension en cuestion y genere los stubs en la ruta destino.
    2. script para aplicar x migraciones desde la ultima generada si no se recibe parametro aplica todas
    3. script para deshacer la migracion, que deshace x revisiones desde la ultima aplicada
    4. script para instalar, crea las tablas de migracion y aplica, si existen las migraciones existentes de la extension.
    4. script para desinstalar

Todos estos scripts forman parte de cada extension, es decir cada extension debe tener la capacidad de generar migraciones por si misma y esta capacidad es inyectada mediante este paquete.


Changelog 08-12-2024
the project will be in several computers at the same time, each computer generating its own set of migrations. i think the right thing to do would be to make them collision with git so that the user will have to merge them, keeping the state of the database from breaking, as each migration can introduce conflicting changes to the database.
we cant rely on the internal state of a local database, as each local instance will have its own state. what we CAN store in the database is if certain migration run or rolled back, and the migrations run in this database.

1. With this in mind, in order to generate a migration and its datafix (if needed) we will need to see the last migration id in the migration directory. We will only use the number on its name, and maybe think of a way to stablish some sort of dependency between migrations.

2. migrations must be stored in the package, instead of an outer directory and must take part in commits

3. migrations can establish dependency relations. to be run they need any other dependency to have been applied

4. will need to do a configuration script to create directories and configuration file for certain extension as well as the tables in the extension schema.

5. determine created_at with os.path.getctime(path)


Changelog 09-12-2024
Been thinking about the usefulness of the tool because there is no need to handle migrations through python if we add the chance to run sql scripts on the database. But i realised that the main idea of the tool is to keep track of types defined in python and reflect changes applied on them into the database. so the main idea behind the building tool is to ensure that the final status of the python type is compatible with whatever the migration changes are. for example, suppose we had an existing table test_table and we need to add a column test_colum of type int8, then, to apply those changes, the user would need to create a migration that not only generates the proper sql commands, but also ensures the type test_table has the test_column in its definition, and that the type is effectively what the migration says it is.
